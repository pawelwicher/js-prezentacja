Optymalizacja JS — silnik V8

Wstęp

⚡ Szybkość działania
Złożoność algorytmiczna Największe zyski. Zagnieżdżone pętle O(n²) na dużych danych potrafią zabić wydajność. Map / Set (O(1)) zamiast Array.includes / indexOf (O(n)).
Operacje na DOM Drogie — batchuj zmiany, buduj poza DOM-em i wstawiaj raz. Unikaj mieszania odczytu właściwości wymuszających reflow (offsetHeight, getBoundingClientRect) z zapisami.
Pętle i metody tablicowe for jest zwykle szybszy niż forEach / map. Łańcuchy .filter().map().reduce() iterują tablicę wielokrotnie — przy dużych zbiorach lepsza jest jedna pętla.
Asynchroniczność Promise.all() zamiast sekwencyjnego await w pętli gdy operacje są niezależne. Ciężkie obliczenia synchroniczne — przenieś do Web Workera.
Debounce / throttle Dla zdarzeń scroll, resize, input — ogranicza liczbę wywołań handlera.
JIT-friendly kod V8 lubi obiekty o stałym kształcie (monomorficzne). Dodawanie i usuwanie pól w hot pathach degraduje wydajność przez deoptymalizację.
🧠 Zużycie pamięci
Wycieki pamięci Listenery niewyrejestrowane przy usuwaniu elementu, setInterval trzymający referencje, closures trzymające duże obiekty, przypadkowe zmienne globalne, detached DOM nodes.
Struktury danych WeakMap / WeakSet gdy klucze mogą być garbage-collected. Map jest pamięciowo cięższy niż zwykły obiekt, ale szybszy przy częstych dodawaniach/usuwaniach.
Kopiowanie vs mutacja Podejście niemutowalne ({...obj}, [...arr]) jest czyste, ale generuje dużo śmieci. W hot pathach czasem warto mutować lokalnie.
Stringi i konkatenacja Przy budowaniu długich stringów w pętli array.join('') jest bezpieczniejszy niż +=.
TypedArray Float32Array, Uint8Array — dużo bardziej kompaktowe niż zwykłe Array przy danych liczbowych.
Streaming Przy dużych plikach / odpowiedziach API — streamy zamiast wczytywania wszystkiego do pamięci naraz.
Twierdzenie Knutha
„Premature optimization is the root of all evil." — Donald Knuth, 1974
Pełny cytat: „We should forget about small efficiencies, say about 97% of the time: premature optimization is the root of all evil. Yet we should not pass up our opportunities in that critical 3%."
Reguła trzyma się mocno: zoptymalizuj algorytm i strukturę danych najpierw (O-notacja, lokalność cache, alokacje), a mikro-optymalizacje JIT-a stosuj tylko w zmierzonych hot pathach. Większość kodu aplikacyjnego nigdy nie powinna ich potrzebować — i odwrotnie, w silnikach gier, parserach, runtime'ach czy bibliotekach numerycznych mogą stanowić różnicę między działaniem a niedziałaniem.
📏 Zanim zaczniesz optymalizować — zmierz. DevTools Performance i Memory tab pokazują gdzie naprawdę leży problem. Intuicja często zawodzi — profiler nie kłamie.
