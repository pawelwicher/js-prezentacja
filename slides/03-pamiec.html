Optymalizacja JS — silnik V8

Zarządzanie pamięcią w JS

📦 Stos (Stack)
Prymitywy — number, boolean, string, null, undefined, symbol, bigint
Stały rozmiar, kopiowanie przez wartość
Automatyczne zarządzanie — push/pop przy wywołaniach funkcji
Bardzo szybki dostęp (LIFO, ciągły blok)
🌐 Sterta (Heap)
Obiekty, tablice, funkcje, domknięcia
Zmienne trzymają referencje — dwa wskaźniki, jeden obiekt
Dynamiczny rozmiar, zarządza GC
Wycieki zawsze dotyczą sterty — nie stosu
stos-sterta.js
let a = 5;          // wartość 5 na stosie
let b = a;          // niezależna kopia — zmiana b nie rusza a

let obj  = { x: 1 }; // obiekt na stercie, obj to referencja
let obj2 = obj;       // ta sama referencja → ten sam obiekt
obj2.x = 99;
console.log(obj.x);  // 99 — oba wskazują to samo miejsce w pamięci
🔄 Cykl życia pamięci: alokacja (tworzenie wartości) → użycie (odczyt/zapis) → zwolnienie (GC uznaje, że obiekt jest nieosiągalny). GC nie pyta "ile referencji mnie wskazuje" — pyta "czy da się do mnie dojść od rootów".
Legenda
Roots — globalThis, call stack, timery, listenery DOM
Osiągalny — da się dojść od rootów → nie zostanie usunięty
Nieosiągalny — wyciek lub cykl → GC usunie przy następnym sweepie
♻️ Reference counting (stary algorytm) nie radził sobie z cyklami — dwa obiekty wzajemnie się wskazujące miały licznik = 1 i nigdy nie były zwalniane. Mark-and-sweep ten problem rozwiązuje, bo patrzy z perspektywy osiągalności od rootów, a nie liczby referencji.
Silnik: V8 (Chrome / Node.js) — SpiderMonkey (Firefox) i JavaScriptCore (Safari) stosują analogiczne podejście generacyjne
⚡ Young generation — algorytm Scavenge
Przestrzeń podzielona na dwie półprzestrzenie: From-space i To-space (łącznie ~1–8 MB)
Każdy nowy obiekt jest alokowany w From-space. Po jego zapełnieniu uruchamiany jest cykl Scavenge (algorytm Cheneya)
Kolektor kopiuje wyłącznie obiekty osiągalne do To-space, po czym obie półprzestrzenie zamieniają role
Martwe obiekty nie są usuwane explicite — całe From-space jest resetowane przez przesunięcie wskaźnika alokacji. Obiekty, których nikt nie skopiował, zostają nadpisane przy kolejnych alokacjach
Złożoność czasowa jest proporcjonalna do liczby żywych obiektów — wysoka śmiertelność przekłada się na krótki czas kolekcji
Typowa pauza: 1–5 ms; cykl uruchamiany jest często, lecz przewidywalnie
🏛️ Old generation — Mark-Sweep-Compact
Obiekty, które przeżyły co najmniej dwa cykle Scavenge, podlegają promocji do old generation
Mark — kolektor przechodzi graf osiągalności od rootów; faza wykonywana częściowo współbieżnie na dedykowanych wątkach
Sweep — nieosiągalne komórki są rejestrowane na listach wolnych bloków i udostępniane alokatorowi
Compact — żywe obiekty są zagęszczane w celu ograniczenia fragmentacji; uruchamiane selektywnie ze względu na koszt operacji
Pauzy są dłuższe, lecz praca jest rozbita inkrementalnie i współbieżnie, co eliminuje pojedyncze długie zatrzymania wątku JS
💡 Hipoteza generacyjna (generational hypothesis): empiryczna obserwacja, że zdecydowana większość obiektów ma krótki czas życia. V8 eksploatuje tę właściwość, stosując dwa odrębne kolektory o różnych charakterystykach czasowych. Promocja do old generation jest punktem krytycznym — obiekt, który miał żyć przez milisekundy, a awansował wskutek niezwolnionego listenera lub nieograniczonego cache'a, będzie obciążał kosztowniejszy cykl Mark-Sweep-Compact przez cały czas życia aplikacji.
1. Zmienne globalne
Brak let/const/var tworzy zmienną globalną żyjącą przez cały czas aplikacji.
function load() { data = fetchAll(); // brak let → window.data } function load() { const data = fetchAll(); // lokalna }
✓ Zawsze 'use strict' lub moduły ES
2. Zapomniane timery
setInterval trzyma referencję do callbacka, a callback do wszystkiego, co domyka.
setInterval(() => { el.textContent = getData(); }, 1000); // nigdy nie jest czyszczony const id = setInterval(() => { el.textContent = getData(); }, 1000); onDestroy(() => clearInterval(id));
✓ Zapisuj ID, wołaj clearInterval(id) przy cleanup
3. Listenery DOM
Listener i jego domknięcie (np. heavyContext) zostają w pamięci po usunięciu elementu.
const big = new Array(1e6).fill(0); btn.addEventListener('click', () => { use(big); // big żyje tak długo jak btn }); const ac = new AbortController(); btn.addEventListener('click', handler, { signal: ac.signal }); onDestroy(() => ac.abort());
✓ AbortController lub removeEventListener
4. Detached nodes
Element usunięty z DOM, ale wciąż trzymany przez zmienną JS lub cache. Widoczny w DevTools jako "Detached HTMLElement".
const rows = []; function addRow() { const tr = table.insertRow(); rows.push(tr); // rows trzyma usunięte table.remove(); } let rowRef = null; rowRef = table.insertRow(); table.remove(); rowRef = null; // GC może zebrać
✓ Nulluj referencje po usunięciu z DOM
5. Cache bez limitu
Nieskończenie rosnący cache = {} lub Map z setkami tysięcy wpisów.
const cache = new Map(); function get(key) { if (!cache.has(key)) cache.set(key, compute(key)); return cache.get(key); // rośnie bez końca } const cache = new WeakMap(); // klucz-obiekt → GC może zebrać wpis function get(obj) { if (!cache.has(obj)) cache.set(obj, compute(obj)); return cache.get(obj); }
✓ LRU cache lub WeakMap (klucze mogą być GC-owane)
6. Closures uwięziające kontekst
Domknięcie używa tylko small, ale gdy jest eval / with — całe scope zostaje.
function outer() { const big = new Array(1e6); const small = 42; return () => { eval(''); // zatrzymuje całe scope return small; }; } function outer() { const big = new Array(1e6); const small = 42; return () => small; // big może być GC }
✓ Przekazuj tylko to, co potrzebne; unikaj eval
🔬 Diagnostyka w Chrome DevTools → Memory: Heap snapshot — porównaj dwa snapshoty, szukaj rosnących struktur; Allocation on timeline — kiedy i co alokuje; Performance → Memory — schodkowy wykres po każdym GC to klasyczny sygnał wycieku. W Node.js: --inspect + DevTools lub process.memoryUsage().
