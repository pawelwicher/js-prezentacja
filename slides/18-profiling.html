Optymalizacja JS — silnik V8

Profiling w praktyce — Chrome DevTools

JAK CZYTAĆ FLAME GRAPH
Oś X = czas — szerokość bloku to ile czasu dana funkcja (i jej callees) spędziła na stosie. Nie jest to oś chronologiczna — identyczne klatki stosu są scalane.
Oś Y = głębokość stosu — blok na górze (root) to najwyższy poziom wywołania; bloki poniżej to wywołania zagnieżdżone.
Szukaj szerokich bloków — szeroka klatka to gorące miejsce. Jeśli szeroki blok ma szerokie dzieci, problem leży głębiej. Jeśli nie ma dzieci lub są wąskie — to sam jest bottleneckiem.
Odróżnij self time od total time — self time = czas w samej funkcji bez callees. Total time = cały stos. Optymalizuj funkcje z dużym self time.
KATEGORIE W PROFILERZE CHROME
(program)Kod JS — Twój JavaScript i biblioteki. Szukaj tu wąskich gardeł aplikacji.
(garbage collector)Czas GC. Częste piki = zbyt wiele alokacji. Rozwiązanie: object pooling, TypedArray, WeakMap.
(idle)Przeglądarka czeka. Dobrze — oznacza, że wątek główny nie jest zablokowany.
(renderer)Renderowanie: layout, paint, composite. Długie bloki tu = zbyt wiele operacji DOM lub layout thrashing.
(compilation)JIT — V8 kompiluje hot functions. Widoczne przy starcie. Nie powinno pojawiać się w ustabilizowanej pętli.
WORKFLOW — jak znaleźć i potwierdzić bottleneck
1
Nagraj profil w warunkach produkcyjnych — otwórz DevTools → Performance → nagraj 10–30 s rzeczywistego użycia. Unikaj nagrywania zimnego startu jeśli badasz steady-state.
2
Znajdź długi task w głównym wątku — zaznacz przedział czasowy z problemem. Długie paski w "Main" Thread to "Long Tasks" (>50 ms) blokujące responsywność.
3
Rozwiń flame graph poniżej — zidentyfikuj najszerszy blok z dużym self time. Kliknij go, żeby zobaczyć plik i linię.
4
Zmierz before/after — użyj performance.mark() i performance.measure() żeby precyzyjnie zmierzyć zmianę. Nie ufaj subiektywnym odczuciom.
5
Sprawdź GC pauses — zaznacz kategorię "GC" w timeline. Częste krótkie pauzy wskazują na high allocation rate; rzadkie długie — na promowanie dużych obiektów do old generation.
METRYKI DO OBSERWOWANIA
FPS (klatki/s) — cel: stałe 60 fps = klatka co 16.6 ms. Spadki poniżej 30 fps są widoczne gołym okiem jako "jank".
Long Tasks — zadania >50 ms blokują wątek główny i uniemożliwiają odpowiedź na input. Widoczne jako czerwone trójkąty w profilerze.
Heap size — rosnący heap przy stabilnym użyciu = wyciek pamięci. Zbyt częste GC = za dużo alokacji.
Layout/Paint — wymuszony reflow (layout thrashing) pojawia się gdy JS odczytuje geometrię (offsetWidth) zaraz po zapisie do DOM w tej samej klatce.
TYPOWE PUŁAPKI
Pomiar w trybie deweloperskim — DevTools i extensions spowalniają JS. Profiluj w trybie incognito bez rozszerzeń.
Tylko zimny start — JIT rozgrzewa się przez pierwsze sekundy. Nagraj profil po kilku sekundach rozgrzewki.
console.log() trzyma referencje — przekazanie obiektu do console.log utrzymuje go przy życiu w panelu DevTools. Fałszuje pomiar wycieku.
CPU throttling — użyj 4× lub 6× CPU slowdown żeby symulować słabsze urządzenia mobilne.
HEAP SNAPSHOT
Zrzut stanu sterty w danym momencie. Pokaż widok Comparison między dwoma snapshotami żeby zobaczyć co zostało zaalokowane i nie zwolnione.
Sortuj po Retained Size — to ile pamięci zostanie zwolnione gdy obiekt zostanie GC'd (włącznie z obiektami, które tylko ten obiekt utrzymuje przy życiu).
Szukaj Detached DOM nodes w filtrze — węzły DOM odłączone od drzewa ale nadal trzymane przez JS.
ALLOCATION TIMELINE
Nagrywa alokacje w czasie rzeczywistym. Niebieski pasek = obiekt zaalokowany i nadal żywy. Szary = zwolniony przez GC.
Wybierz wycinek czasu gdzie heap rośnie i zbadaj co zostało zaalokowane — zobaczysz stos wywołań dla każdego obiektu.
Świetne do diagnozy retention loops — np. listener trzymający zamknięcie trzymające DOM trzymający element z handlerem.
ALLOCATION SAMPLING
Lżejszy tryb — próbkuje alokacje zamiast rejestrować każdą. Mały overhead, można włączyć na dłużej.
Pokazuje które funkcje odpowiadają za największy wolumen alokacji — dobry punkt startowy gdy nie wiesz gdzie szukać.
Pamiętaj: duże alokacje to niekoniecznie wyciek — liczy się czy GC może je zwolnić. Sprawdź czy heap stabilizuje się po cyklu pracy.
✗  Pomiar przez Date.now() — nieprecyzyjny
// Date.now() ma rozdzielczość 1 ms i może być throttlowany
const start = Date.now();
doSomething();
const elapsed = Date.now() - start;
console.log(elapsed + ' ms'); // niewystarczająca precyzja
✓  Performance API — do 5 µs rozdzielczości
// Precyzyjny pomiar z nazwanymi markerami
performance.mark('start-parse');
const result = parseData(raw);
performance.mark('end-parse');

performance.measure('parse', 'start-parse', 'end-parse');

const [entry] = performance.getEntriesByName('parse');
console.log(entry.duration.toFixed(3) + ' ms');
// Widoczne w DevTools Performance → Timings
PerformanceObserver — monitorowanie w tle
// Obserwuj Long Tasks bez blokowania głównego wątku
const obs = new PerformanceObserver(list => {
  for (const entry of list.getEntries()) {
    if (entry.duration > 50) {
      console.warn('Long Task:', entry.duration.toFixed(1), 'ms');
      // wyślij do systemu monitorowania
    }
  }
});
obs.observe({ type: 'longtask', buffered: true });
measureUserAgentSpecificMemory — pamięć w prod
// Dostępne tylko w cross-origin isolated context (COOP/COEP)
if ('measureUserAgentSpecificMemory' in performance) {
  const mem = await performance.measureUserAgentSpecificMemory();
  console.log('Heap:', mem.bytes / 1024 / 1024, 'MB');
  // mem.breakdown — podział wg typu zasobu
}

// Alternatywa: performance.memory (Chrome, niestandard)
console.log(performance.memory?.usedJSHeapSize);
