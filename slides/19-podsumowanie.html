kształt obiektów i JIT
Wszystkie pola w konstruktorze, zawsze w tej samej kolejności — {x,y} ≠ {y,x}
✗ delete obj.prop → dictionary mode; ✓ obj.prop = null
Jedna funkcja = jeden kształt argumentu → monomorphic IC → najszybszy kod
tablice
Literał [1,2,3] = PACKED_SMI; ✗ new Array(N), delete arr[i], mieszanie typów
Degradacja elements kind jest nieodwracalna — jedno push(0.5) wystarczy
Duże dane liczbowe → TypedArray (4–32× mniej pamięci, subarray bez kopii)
struktury danych
Set.has O(1) zamiast includes O(n); [...new Set(arr)] do deduplikacji
Map przy dynamicznych kluczach; Object szybszy przy stałym zestawie pól
Płytka kopia: spread; głęboka: structuredClone
pamięć

już nieaktualne — przestań się martwić
„try/catch blokuje optymalizację" — prawda za Crankshafta; TurboFan optymalizuje
„join('') zamiast +=" — V8 buduje rope; += zwykle szybsze
„cache'uj arr.length, ++i zamiast i++" — JIT robi to sam
„małe funkcje są drogie" — gorące, monomorficzne są inline'owane
to nadal realnie kosztuje
delete obj.prop — dictionary mode + unieważnione inline cache
zmiana kształtu w hot path — nowe hidden classes, deopt
megamorficzne call-site (>4 kształty) — koniec specjalizacji i inliningu
tablica jako kolejka przez shift() — O(n²), zmierzone: 200k shiftów = 19 s
Złota zasada: zmierz, zanim zoptymalizujesz. V8 zmienia się co kilka tygodni — rada „zawsze rób X" szybko się starzeje, profiler na Twojej wersji silnika nie. Mikro-optymalizacje tylko w zmierzonych hot pathach.
