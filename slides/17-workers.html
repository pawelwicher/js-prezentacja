Web Workers

Worker ma własną stertę i własny GC — ciężkie obliczenia nie blokują UI. Haczyk: postMessage domyślnie kopiuje dane (structured clone). Duże bufory transferuj — zamiana O(n) kopii w O(1).
dobre przypadki
parsowanie dużych JSON/CSV, kompresja, szyfrowanie, obliczenia numeryczne, obrazy, audio
złe przypadki
dostęp do DOM (brak), krótkie zadania (start workera to kilka–kilkanaście ms), małe dane w pętli
worker pool
N workerów przy starcie + kolejka zadań — koszt startu amortyzuje się przez całe życie aplikacji
transferable objects
ArrayBuffertransferźródło odłączone (byteLength === 0) — worker przejmuje bufor na wyłączność
MessagePort / ImageBitmaptransferkanały komunikacji, klatki video/canvas bez kopiowania pikseli
SharedArrayBufferwspółdzielonyoba wątki widzą tę samą pamięć — wymaga Atomics + nagłówków COOP/COEP
zwykły obiekt JSkopiastructured clone — koszt O(rozmiar danych)
✗ kopia — structured clone
const big = new Float32Array(10_000_000); // 40 MB

worker.postMessage({ data: big });
// kopia ~10–30 ms + 2× pamięć
// (big nadal dostępne po stronie głównej)
✓ transfer — zero-copy
const big = new Float32Array(10_000_000);

worker.postMessage({ data: big }, [big.buffer]);
// O(1) — bufor przeniesiony, nie skopiowany
// big.buffer.byteLength === 0 — odłączony!
Reguła: wysyłasz TypedArray/ArrayBuffer i nie potrzebujesz go po stronie głównej? Zawsze dodaj do listy transfer. SharedArrayBuffer bez Atomics = wyścig danych.
