Web Workers — wielowątkowość i transferables

IZOLACJA STERTY
Każdy Worker ma własną, odizolowaną stertę V8. Nie współdzielą pamięci z wątkiem głównym — brak wyścigów danych, brak blokad.
GC każdego workera działa niezależnie. Alokacje w workerze nie powodują pauz GC w wątku głównym i odwrotnie.
Konsekwencja: wyciągnięcie ciężkich obliczeń do workera odciąża główny wątek i eliminuje jank w animacjach i UI.
KOMUNIKACJA — postMessage
Domyślnie: kopiowanie strukturalne — postMessage(data) serializuje dane algorytmem structured clone i kopiuje je do drugiej sterty. Koszt = O(rozmiar danych).
Structured clone obsługuje: Date, Map, Set, ArrayBuffer, Blob, cykliczne referencje. Nie obsługuje: funkcji, DOM, klas z metodami.
Alternatywa zero-copy: transferables — patrz niżej.
KIEDY UŻYWAĆ WORKERÓW
✓ Dobre przypadki: parsowanie dużych plików JSON/CSV, kompresja, szyfrowanie, obliczenia numeryczne, generowanie obrazów, przetwarzanie audio.
✗ Złe przypadki: zadania wymagające dostępu do DOM (worker nie ma dostępu), krótkie operacje (overhead tworzenia workera > zysk), pętle z małymi danymi.
Worker pool: twórz N workerów przy starcie aplikacji i kolejkuj do nich zadania. Koszt tworzenia workera (~1 ms) amortyzuje się przez cały czas życia.
TRANSFERABLE OBJECTS — zero-copy transfer
Typ Transfer możliwy? Co się dzieje ze źródłem? Kiedy używać
ArrayBuffer TAK Bufor staje się odłączony (byteLength === 0) — nie można już go czytać po stronie nadawcy Duże dane binarne, obrazy, audio, dane sensoryczne
MessagePort TAK Port przechodzi do workera — dwukierunkowy kanał komunikacji Trwałe, niskie-latency kanały między workerami
ImageBitmap TAK Źródło odłączone; GPU-resident texture transferowana bez kopiowania pikseli Przenoszenie klatek video/canvas między wątkami
SharedArrayBuffer DZIELONY Oba wątki mają dostęp do tej samej pamięci — wymaga Atomics do synchronizacji Bardzo wydajne dzielenie danych; wymaga COOP/COEP headers
Zwykły obiekt JS NIE Structured clone — kopia; oryginał niezmieniony Małe dane konfiguracyjne, wyniki
✗  Kopiowanie danych (structured clone)
// Main thread
const bigArray = new Float32Array(10_000_000);
fillData(bigArray);

// postMessage bez transferu → kopiuje 40 MB
worker.postMessage({ data: bigArray });

// bigArray nadal dostępne po stronie głównej —
// ale worker dostał kopię, mamy dwa bufory w pamięci
// Czas transfer ~200–400 ms dla 40 MB
✓  Transfer (zero-copy)
// Main thread
const bigArray = new Float32Array(10_000_000);
fillData(bigArray);

// Drugi argument to lista transferable objects
// Bufor jest przenoszony, nie kopiowany — O(1) czas
worker.postMessage(
  { data: bigArray },
  [bigArray.buffer]   // ← transfer lista
);

// bigArray.buffer.byteLength === 0 — odłączony!
// Worker ma wyłączny dostęp do bufora
REGUŁA KCIUKA
Zawsze transferuj ArrayBuffer
Jeśli wysyłasz TypedArray lub ArrayBuffer do workera i nie potrzebujesz go dalej po stronie głównej, dodaj go do listy transferable. Zamienia O(n) kopię w O(1).
Worker pool zamiast tworzenia na żądanie
Koszt tworzenia workera to ~1–5 ms plus ładowanie skryptu. Dla zadań <10 ms overhead przewyższy zysk. Utrzymuj pulę gotowych workerów.
SharedArrayBuffer = synchronizacja
Współdzielona pamięć bez Atomics to wyścig danych. Używaj Atomics.wait() / Atomics.notify() lub projektuj protokół bez blokad.
