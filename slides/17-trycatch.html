Optymalizacja JS — silnik V8

try/catch a deoptymalizacja TurboFan

DLACZEGO try/catch SZKODZI JIT
TurboFan musi wygenerować dodatkowe tabele obsługi wyjątków i punkty przywrócenia stosu. Sprawia to, że kod wewnątrz try jest trudniejszy do analizy i rzadziej optymalizowany.
Historycznie V8 w ogóle nie optymalizował funkcji zawierających try/catch. Nowsze wersje (od V8 ~9.x) optymalizują je częściowo, ale inlining funkcji z try/catch pozostaje zablokowany.
Wyjątek zrzucony w środku try wymaga odwinięcia stosu — to zawsze jest wolna ścieżka. Wyjątki nie powinny być używane do sterowania przepływem.
KIEDY TO MA ZNACZENIE
Hot loop — try/catch wewnątrz pętli wykonywanej miliony razy to najgorszy scenariusz: każda iteracja niesie koszt mechanizmu wyjątków.
Małe funkcje pomocnicze — jeśli helper wywoływany z gorącej pętli sam zawiera try/catch, TurboFan nie zinlinuje go do pętli, tracąc całą optymalizację.
Parsowanie JSON jako flow control — łapanie SyntaxError z JSON.parse jest drogie; lepiej walidować dane przed parsowaniem.
PRAWIDŁOWE WZORCE
Wypchnij try na zewnątrz pętli — obsługuj błędy na poziomie wywołującego, nie w środku gorącej ścieżki.
Wydziel hot kernel — wyciągnij obliczenia do oddzielnej funkcji bez try/catch; zostanie ona zinlinowana przez TurboFan.
Używaj wyników zamiast wyjątków — zwracaj null / undefined przy błędach przewidywalnych; rzucaj wyjątki tylko dla warunków naprawdę wyjątkowych.
✗  try/catch w hot path
// try/catch wewnątrz pętli — brak inliningu kernela
function processAll(items) {
  let sum = 0;
  for (let i = 0; i < items.length; i++) {
    try {
      sum += heavyKernel(items[i]); // nie zostanie zinlinowane!
    } catch (e) {
      // obsługa błędu
    }
  }
  return sum;
}

// Wyjątek jako flow control — bardzo wolne
function safeParse(str) {
  try {
    return JSON.parse(str);
  } catch {
    return null; // rzucany wyjątek = odwijanie stosu
  }
}
✓  try/catch poza hot path
// Wypchnij try na zewnątrz pętli
function processAll(items) {
  try {
    let sum = 0;
    for (let i = 0; i < items.length; i++) {
      sum += heavyKernel(items[i]); // inlining działa ✓
    }
    return sum;
  } catch (e) {
    return 0;
  }
}

// Walidacja zamiast łapania wyjątku
function safeParse(str) {
  if (typeof str !== 'string' || str[0] !== '{')
    return null;        // tania ścieżka bez wyjątku
  return JSON.parse(str);
}

REGUŁA KCIUKA
try/catch poza gorącą pętlą
Owijaj pętlę jednym try zamiast wstawiać try wewnątrz każdej iteracji. Logika błędów i logika obliczeniowa — w osobnych funkcjach.
Wyjątki to nie flow control
Rzucanie wyjątku = odwijanie stosu + alokacja obiektu Error. Dla przewidywalnych błędów (brak wartości, zły format) zwracaj wartownik zamiast rzucać.
Nowoczesny V8 jest lepszy
Od V8 9.x try/catch jest mniej destrukcyjne niż historycznie, ale inlining przez granicę try nadal nie działa. Reguła wypchnięcia try na zewnątrz pozostaje ważna.
