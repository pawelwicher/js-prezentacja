Optymalizacja JS — silnik V8

Cheat sheet — co zapamiętać

🧠 Pamięć i GC
Wyrejestruj listenery i timery przy usuwaniu komponentu (AbortController, clearInterval)
Użyj WeakMap / WeakSet gdy klucz to obiekt spoza Twojej kontroli — GC może go zebrać
Nulluj referencje do detached DOM nodes — same nie znikną
Ogranicz cache do LRU lub WeakMap — nieograniczony Map to wyciek
Unikaj eval i with — zamrażają całe scope w domknięciu
⚙️ Kształt obiektów i JIT
Inicjuj wszystkie pola w konstruktorze, zawsze w tej samej kolejności
{x,y} i {y,x} to dwie różne Hidden Classes — trzymaj jedną kolejność
Nie używaj delete obj.prop — degraduje do dictionary mode; zastąp null
Nie dodawaj pól warunkowo po stworzeniu obiektu — każde nowe pole tworzy nową HC
Jedna funkcja = jeden kształt argumentu → monomorphic IC → najszybszy kod JIT
📦 Tablice — Elements Kinds
Zacznij od literału z wartościami: [1,2,3] → PACKED_SMI — najszybszy layout
Nie używaj new Array(N) do inicjalizacji — tworzy HOLEY od razu; użyj Array.from
Nie używaj delete arr[i] — tworzy dziurę; użyj splice
Jedno push(0.5) na tablicy SMI degraduje ją do DOUBLE — nieodwracalne
Do dużych jednorodnych danych liczbowych: Float32Array / Int32Array — 4–32× mniej pamięci
subarray() na TypedArray zwraca widok bez kopii — O(1) pamięć i czas
🔍 Struktury danych
Set.has(x) O(1) zamiast Array.includes(x) O(n) — przy >100 elementach zawsze Set
[...new Set(arr)] O(n) zamiast filter+indexOf O(n²) do deduplikacji
Map zamiast Object gdy klucze są dynamiczne lub często usuwane — stabilne O(1) bez degradacji
Object z hidden class jest szybszy od Map przy stałym zestawie kluczy i częstym odczycie
Do klonowania płaskiego: spread {...obj} — najszybszy; deep: structuredClone — poprawny semantycznie
Object pool eliminuje alokacje w hot path — zero śmieci dla GC w pętlach animacji / symulacji
MITY WYDAJNOŚCIOWE — co już nieaktualne, co wciąż prawdziwe
✓ Już można przestać się tym martwić
„try/catch uniemożliwia optymalizację" Prawda dla starego Crankshafta. TurboFan optymalizuje funkcje z try/catch — nie trzeba już wyciągać pętli na zewnątrz.
„let/const są wolniejsze od var" Różnica jest pomijalna, a per-iteration binding daje poprawne domknięcia w pętli. Używaj const domyślnie.
„for jest zawsze szybszy niż forEach/map" Dla monomorficznych callbacków różnica bywa w granicach szumu. Czytelność wygrywa poza zmierzonymi hot-pathami.
„Cache'uj arr.length, używaj ++i zamiast i++" JIT i tak to robi. Mikro-sztuczki z lat 2000. nie dają dziś nic mierzalnego.
„Małe funkcje są drogie — wklejaj ręcznie" TurboFan inline'uje gorące, monomorficzne funkcje. Abstrakcja zwykle nic nie kosztuje.
✗ To NADAL realnie kosztuje
delete obj.prop Wciąż degraduje obiekt do dictionary mode i unieważnia inline cache. Zamiast tego obj.prop = null.
Zmiana kształtu obiektu w hot path Dodawanie pól po konstrukcji, różna kolejność pól → nowe Hidden Classes i deopt. To dalej prawda.
Megamorficzne call-site >4 kształty w jednym miejscu → koniec specjalizacji i koniec inliningu. Realny koszt.
Tablica jako kolejka przez shift() Nadal O(n²). Memmove na każdym kroku nie zniknął.
Nieograniczony cache i zagnieżdżone kwantyfikatory regex Wyciek pamięci i catastrophic backtracking to problemy ponadczasowe — i często groźne dla bezpieczeństwa.
🧭 Mity biorą się z prawdziwych obserwacji — sprzed lat. V8 zmienia się co kilka tygodni, więc rada „zawsze rób X" szybko się starzeje. Jedyna ponadczasowa zasada: zmierz na swojej wersji silnika, zanim przepiszesz kod w imię wydajności.
📏 Złota reguła: zmierz zanim zaoptymalizujesz. DevTools → Performance i Memory tab pokazują gdzie leży prawdziwy problem. Mikro-optymalizacje JIT stosuj tylko w zmierzonych hot pathach — w kodzie aplikacyjnym rzadko są potrzebne.
