Optymalizacja JS — silnik V8

TypedArray — zużycie pamięci

JAK V8 PRZECHOWUJE LICZBY W ZWYKŁEJ TABLICY
SMI_ELEMENTS — liczby całkowite mieszczące się w 31 bitach; trzymane bezpośrednio jako tagged integer, bez alokacji na stercie
DOUBLE_ELEMENTS — floaty lub duże inty; V8 unboxuje je do ciągłego bloku (FixedDoubleArray), ~8 B/element — zbliżone do Float64Array
OBJECT_ELEMENTS — mieszane typy lub po wrzuceniu null / stringa; każda liczba pakowana do HeapNumber na stercie — pointer (8 B) + nagłówek + wartość = ~32 B/element
Pułapka: jedna operacja arr.push(null) lub arr[i] = undefined konwertuje całą tablicę na OBJECT_ELEMENTS — wszystkie elementy przepakowywane, zużycie pamięci skacze 4×
JAK V8 PRZECHOWUJE LICZBY W TYPEDARRAY
ArrayBuffer — surowy, ciągły blok bajtów bez żadnego tagowania ani nagłówków per-element; jeden obiekt na stercie niezależnie od rozmiaru
Widok (view) — TypedArray to tylko metadane (pointer, offset, length); wiele widoków może nakładać się na ten sam bufor bez kopiowania danych
Rozmiar deterministyczny — zawsze dokładnie tyle bajtów ile wynika z typu × liczba elementów; V8 nie może zmienić reprezentacji w trakcie działania
GC — cały ArrayBuffer to jeden węzeł w grafie obiektów; GC skanuje go w O(1) niezależnie od tego ile elementów zawiera

✗  Array.slice() — zawsze kopiuje dane
const big = new Array(1_000_000).fill(1.0);

// slice tworzy nową tablicę i kopiuje elementy
// O(n) czas i O(n) pamięć
const chunk = big.slice(0, 10_000); // kopia!
✓  TypedArray.subarray() — widok bez kopii
const big = new Float64Array(1_000_000).fill(1.0);

// subarray zwraca nowy widok na TEN SAM bufor
// O(1) czas, zero dodatkowej pamięci
const chunk = big.subarray(0, 10_000); // widok!
// chunk i big dzielą ten sam ArrayBuffer
