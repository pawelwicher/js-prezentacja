Optymalizacja JS — silnik V8

Jak V8 śledzi kształt obiektów

CO TO JEST HIDDEN CLASS (MAP)
V8 nie przechowuje nazw właściwości w każdym obiekcie. Zamiast tego tworzy wewnętrzną strukturę Hidden Class (w kodzie V8 nazywana Map), która opisuje kształt obiektu: jakie pola istnieją i pod jakim offsetem w pamięci.
Obiekty o identycznym zestawie pól (dodawanych w tej samej kolejności) współdzielą jedną Hidden Class. Dostęp do pola to wtedy proste przesunięcie w pamięci — jak w struct w C.
Inline Cache (IC) — przy każdym odczycie obj.x V8 zapamiętuje Hidden Class obiektu i kompiluje bezpośredni skok. Następne wywołanie z tym samym kształtem trafia w gotowy kod maszynowy.
Megamorphic ≠ deopt — zmiana stanu IC (mono→poly→mega) tylko obniża stopień specjalizacji dostępu. Deoptymalizacja to osobne zdarzenie: zoptymalizowany kod TurboFana trafia na nieoczekiwany kształt, zostaje odrzucony i wykonanie wraca do interpretera.
CO NISZCZY HIDDEN CLASS
Różna kolejność właściwości — {x,y} i {y,x} to dwie różne Hidden Classes, mimo tych samych pól.
Dynamiczne dodawanie pól — każde obj.newProp = … po stworzeniu obiektu tworzy nową Hidden Class (transition chain).
delete obj.prop — usuwa pole i może zdegradować obiekt do trybu słownikowego (jak DICTIONARY dla tablic).
Warunkowo inicjowane pola — gdy część obiektów ma pole extra a część nie, IC staje się polymorphic i V8 generuje wolniejszy kod.
Reguła: inicjuj wszystkie pola w konstruktorze, zawsze w tej samej kolejności.
STANY INLINE CACHE — co widzi V8 przy każdym wywołaniu
Monomorphic
1 Hidden Class
IC widział zawsze ten sam kształt. V8 JIT kompiluje dostęp do pola jako stały offset w pamięci — zero lookupów, kod jak w C.
Próg: jeden kształt przez cały czas życia call-site.
Polymorphic
2–4 Hidden Classes
IC widział kilka różnych kształtów. V8 generuje krótką listę sprawdzeń (IC stub): porównuje HC obiektu z każdym zapamiętanym — pierwsze trafienie wygrywa.
Próg V8: do 4 kształtów. Wolniejsze od mono, ale JIT nadal działa.
Megamorphic
> 4 Hidden Classes
IC się poddał — zbyt wiele różnych kształtów. V8 przełącza się na generyczny property lookup (runtime, bez specjalizacji JIT). Każdy dostęp do pola idzie przez słownik kształtów.
Skutek: deoptymalizacja hot patha, znaczny spadek wydajności.
PRZYKŁADY — dobre vs złe wzorce
✗  Niszczy Hidden Class
// 1. Różna kolejność pól → różne Hidden Classes
const a = { x: 1, y: 2 }; // HC1: {x, y}
const b = { y: 2, x: 1 }; // HC2: {y, x} — inna HC!

// 2. Dodawanie pól po stworzeniu → transition chain
function Point(x, y) { this.x = x; this.y = y; }
// new Point → HC0: {} → HC1: {x} → HC2: {x,y}
const p = new Point(1, 2); // HC2
p.z = 3; // transition → HC3: {x,y,z}

// 3. delete niszczy Hidden Class
delete p.x; // HC3 → slow properties (dict mode)
✓  Zachowuje Hidden Class
// 1. Stała kolejność pól → jedna Hidden Class
const a = { x: 1, y: 2 }; // HC1: {x, y}
const b = { x: 9, y: 7 }; // HC1: {x, y} — ta sama ✓

// 2. Wszystkie pola w konstruktorze → brak transition
function Point(x, y) {
  this.x = x; this.y = y;
  this.z = 0; // zawsze — HC kończy się na HC3 ✓
}
// new Point → HC0 → HC1 → HC2 → HC3 (raz, przy JIT)
const p = new Point(1, 2); // HC3: {x,y,z}
p.z = 3; // aktualizacja wartości, nie transition ✓

// 3. null zamiast delete — HC nienaruszona
obj.cache = null; // nadal HC z polem cache ✓
BENCHMARK — sumowanie właściwości, N = 500 000 iteracji, 30 powtórzeń
✓  Monomorphic — 1 HC
// Każdy obiekt ma dokładnie 3 pola:
// x, y, tag — zawsze ta sama nazwa
for (let i = 0; i < N; i++) {
  objs.push({ x: i, y: i*2, tag: 0 });
}
// → jedna HC → V8 JIT kompiluje
//   stały offset dla .x i .y
~  Polymorphic — 4 HC
// 4 różne kształty: tag0..tag3
// IC trzyma stub z 4 sprawdzeniami
for (let i = 0; i < N; i++) {
  objs.push({
    x: i, y: i*2,
    ['tag'+(i%4)]: 0
  });
}
// → JIT nadal działa, ale wolniej
✗  Megamorphic — 32 HC
// 32 różne kształty: tag0..tag31
// IC się poddaje — generic lookup
for (let i = 0; i < N; i++) {
  objs.push({
    x: i, y: i*2,
    ['tag'+(i%32)]: 0
  });
}
// → każdy o.x i o.y przez słownik
Stały kształt vs 32 różne Hidden Classes — różnica w dostępie do tych samych pól.
